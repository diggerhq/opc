## Your organization's computer

Each organization has one **computer**: a cloud VM that runs every Computer session for the organization, from Slack, from `opc` and from the API. It holds the organization's repositories, the tools the agent uses and a cache that keeps the model fast. It has no inbound network port. `opc` reaches it through OpenComputer's edge.

If nobody has used the computer for a while, it may need to start. `opc` says `starting your computer` while that happens, which takes seconds rather than milliseconds.

## Sessions

A **session** is one conversation with the agent, with its own workspace and history. A Slack thread is a session. So is every `opc` run that starts a new one.

- A session belongs to the person who started it, and every member of the organization can see it and talk in it. See [Sharing](/cli/sharing).
- A session is never finished. When nobody uses it for two hours, it **suspends**: the agent process stops and frees its memory. The next message resumes it, with the conversation intact.
- A session has a title, taken from its first message. You can change it with `/title` or `opc rename`.
- A session you are done with can be **archived**: it is left out of `opc ls` and other lists, and nothing else changes. Any new message brings it back.
- Sessions are identified by an id such as `cs_7f3a9k2m4q8r1t6v`. `opc` shows the first characters after the prefix, such as `7f3a`, and accepts any unique prefix of four or more. Prefixes are for people: scripts should use full ids, which never become ambiguous.

### Status

| Status | Meaning | Shown in `opc ls` as |
| --- | --- | --- |
| `starting` | The agent is being started, for a new session or to resume a suspended one | `starting` |
| `running` | The agent is working on a turn | `running` |
| `waiting` | The agent is blocked on an [ask](#asks) that a person must answer | `waiting for you` |
| `idle` | The agent is ready and has nothing to do | `idle` |
| `suspended` | The agent process has stopped. The next message resumes it. | `suspended` |

`waiting` wins over `running` and `suspended`: an open ask always shows.

## The workspace

Each session works in its own **workspace**: a copy of the organization's workspace with every connected repository checked out. What one session changes there is invisible to other sessions. Commits and pull requests are how work leaves it, the same as in Slack.

Your laptop is not part of the workspace. `opc` reads no local file unless you run [`opc push`](/cli/files), and writes none unless you run `opc pull`.

<Note>
Build output and dependency directories, such as `node_modules` and `target`, are pruned from workspaces that have been idle for 24 hours. Source files and git state are kept. The agent reinstalls what it needs on the next turn.
</Note>

## Turns

Everything you send is a **message**, and the agent's work on it is a **turn**. A message you send while a turn runs is delivered in one of three ways:

| Delivery | What happens | Default in |
| --- | --- | --- |
| `steer` | Delivered into the running turn at its next step, so the agent adjusts without stopping | The `opc` prompt, Slack |
| `queue` | Waits, and runs as its own turn after the current one | `opc send`, `opc -p -s`, the API |
| `interrupt` | Stops the running turn and every queued one, then runs | `Esc` in `opc` |

On the command line, `--steer`, `--queue` and `--interrupt` choose the delivery. Programs queue by default so that two of them never change each other's turns. When nothing is running, all three start a new turn. A steered message that the turn ends without reading runs as a new turn. A turn ends as `completed`, `failed` or `cancelled`. The agent's last message in a completed turn is the session's **result**: what `opc -p` prints.

## Asks

Sometimes the agent needs a person before it can go on. It raises an **ask**, and the session's status becomes `waiting` until someone answers.

| Kind | Example | Answered with |
| --- | --- | --- |
| `approval` | "Run `terraform apply` in `infra/`?" | Allow, deny, or allow for the rest of the session |
| `question` | "Should I fix the test or the code?" with choices | A choice, several choices, or your own text |
| `secret` | "I need `STRIPE_API_KEY`" | The value, typed where nobody else can see it, never into the conversation |

Any member can answer an ask from any client. The first answer wins, and every other client shows who answered and where. See [Asks](/terminal/asks).

An ask never expires: a session with an open ask is not suspended for being idle, and the ask waits for someone. A message you send while it is open declines it, and the agent reads the message as its instructions.

## Settings

Each session has a **model**, an **effort** level and a **permission mode**. They start from your organization's defaults and can be changed at any time with `/model`, `/effort` and `/mode`. On the command line they are `--model`, `--effort` and `--mode` (or `--permission-mode`, as in `claude`). A new model or effort applies from the next turn. A new permission mode applies at once, to the running turn too.

| Permission mode | The agent… | Can still ask |
| --- | --- | --- |
| `default` | asks before running commands and editing files that need approval | Approvals, questions, secret requests |
| `acceptEdits` | edits files freely and asks before running commands that need approval | Approvals for commands, questions, secret requests |
| `plan` | reads and plans, and changes nothing until you approve the plan | Approval of the plan, questions, secret requests |
| `auto` | runs without asking for approval; a safety check blocks risky actions instead of asking about them | Questions, secret requests |
| `dontAsk` | never asks for approval, and skips actions that would need it | Questions, secret requests |
| `bypassPermissions` | never asks for approval and runs everything. The default for new sessions, as in Slack. | Questions, secret requests |

A permission mode decides approvals only. Questions and secret requests can open in every mode, because only a person can answer them. In a script, `opc -p --on-ask` decides what happens when one opens.

Your organization sets which modes, models and effort levels are allowed. A session lists them in its [capabilities](/api/reference/objects#capabilities).

## Events

Everything that happens in a session is recorded as an **event**, numbered in order: each message, each turn's start and end, each block of text, each tool call, each ask and its answer. Slack, the dashboard and `opc` all draw a session from these events, which is why they agree. Text also streams as **deltas**, fragments that arrive before the block they belong to is complete. Deltas are not recorded, and a client that misses some loses nothing: the complete block follows.

The [API](/api/overview) exposes the same events.
