Read [Concepts](/concepts) first for what sessions, turns and asks are to a person. This page is the same model for a program: the states, the order of events and the guarantees.

## A session is its event log

Everything that happens in a session is appended to its **event log**, and each event gets the next `seq`: 1, 2, 3, with no gaps. The [session object](/api/reference/objects#session) is a snapshot of that log, and its `lastSeq` says how far the snapshot goes.

So a client can always build an exact view in two steps:

1. Read the session. It is correct as of `lastSeq`.
2. Apply events with `seq` greater than `lastSeq`, from [`GET /events?after=`](/api/http/events) or a WebSocket [attach](/api/websocket/methods#attach).

Events are never changed or removed. An event with a `seq` at or below one you applied is a repeat: skip it. That makes reconnecting safe: attach again with `after` set to the last `seq` you applied, and you get exactly what you missed.

### One writer

Each session's log has exactly one writer at a time, on the computer: the agent process while it runs, and the computer itself while the session has none, because it is suspended, starting or its process stopped. So a message sent to a suspended or starting session is recorded at once, as `message.received` and `turn.queued`, and the agent takes it when it is up. An event is recorded before any client sees it.

### If a computer is lost

The writer's term is numbered by the session's `logEpoch`. It changes only when the computer running a session is lost in the middle of a turn. Then the turn's open tool calls end as `tool.failed`, the turn as `turn.failed` with `runtime_lost`, and the session as `runtime.suspended`, all recorded in the new epoch, starting at the session's `epochStartSeq`.

If `logEpoch` differs from the one you stored, discard what you applied at or after `epochStartSeq` and read again from `epochStartSeq - 1`. This only happens if a computer is lost mid-turn.

### Deltas are not in the log

While the agent writes, its text also streams as **deltas**: `message.delta`, `reasoning.delta` and `tool.delta`, and a subagent's progress as `subagent.progress`, sent only over a WebSocket that asked for them, as `delta` notifications rather than `event`. Deltas have no `seq` and are not stored. They are a preview of a block whose complete text arrives in the matching `message.completed`, `reasoning.completed` or `tool.completed` event, which replaces whatever deltas you drew.

- Text and reasoning deltas are tied to their block by `blockId`, tool output by `callId`. Both are unique in the session, not only in the turn.
- A delta never arrives after its block's completed event. Ignore any delta for a `blockId` or `callId` you have already seen complete.

`subagent.progress` has no completed event: its latest values are folded into the [Subagent](/api/reference/objects#subagent) on every read.

A client that misses deltas, because it connected late, reconnected or was too slow, loses nothing but the preview. See [Flow control](/api/websocket/flow-control).

## Sessions

| From | To | When |
| --- | --- | --- |
| | `starting` | The session is created |
| `starting` | `idle` or `running` | The agent is up. `running` if a message is waiting. |
| `idle` | `running` | A message arrives |
| `running` | `waiting` | The agent raises an ask |
| `waiting` | `running` | Every open ask closed |
| `waiting` | `idle` | The asks were open for 24 hours and expired, and the turn was cancelled. See [Asks and suspension](#asks-and-suspension). |
| `running` | `idle` | The last turn ended and nothing is queued |
| `idle` | `suspended` | Two hours without activity and no subagent running, or a [suspend](/api/http/control#suspend) |
| `suspended` | `starting` | A message, an answer, or a [resume](/api/http/control#resume) |

| Status | The agent process | A message sent now |
| --- | --- | --- |
| `starting` | Starting, or resuming from `suspended` | Is recorded at once, then runs |
| `running` | Working on a turn | Queues, steers or interrupts, by [`ifBusy`](/api/http/turns#if-a-turn-is-running) |
| `waiting` | Blocked on an open ask. Kept running while the ask is open, for up to 24 hours. | Is [held](#messages-while-an-ask-is-open) until the ask closes, unless sent with `interrupt` |
| `idle` | Ready | Runs at once |
| `suspended` | Stopped. Its memory is freed, its workspace and conversation are kept. | Is recorded at once, resumes the session, then runs |

A session never ends. There is no `ended` status and no route to end one: an idle session costs nothing but disk once it is suspended. A session can be `archived`, which hides it from lists and changes nothing else; a new message brings it back.

## Turns

A **turn** is the agent's work on one message. Its status moves forward only:

```
queued ──▶ running ──▶ completed
   │          ├──────▶ failed
   │          └──▶ cancelling ──▶ cancelled
   └────────────────────────────▶ cancelled
```

- Turns run one at a time, in the order they were queued.
- A turn that is `cancelled` has a `reason`. `interrupted`: it was running or queued when an [interrupt](/api/http/control#interrupt) came. `withdrawn`: it was queued, and someone [cancelled it](/api/http/turns#cancel-a-queued-turn) before it ran. `expired`: its asks were open for 24 hours. A running turn is `cancelling` from the interrupt until the agent has stopped, usually under a second.
- A turn that `failed` has an [error](/api/reference/errors#turn-failures). The session stays usable: send another message.
- A message sent with `interrupt` records `message.received` with `interruptedTurnIds`, the turns it stopped, before their `turn.cancelled` events.

### Steered and held messages

A message sent with `steer` while a turn runs does not get a turn of its own. It joins the running turn, and the agent reads it at its next step. The send response's `turn` is that running turn, and `delivery` says what happened.

A message joins a turn only if the turn reads it. If the turn ends before the agent took the message in, the message starts a new turn at once, recorded as `turn.queued` or `turn.started` with a new turn id.

## Asks

An **ask** blocks the turn that raised it until it closes. It closes once, as one of:

| Status | Because |
| --- | --- |
| `answered` | Someone answered it. For a secret ask, someone set the secret. |
| `dismissed` | Someone closed it without an answer. The agent is told and decides how to go on. |
| `interrupted` | Its turn was interrupted, or the session was [suspended](/api/http/control#suspend) |
| `expired` | It was open for 24 hours |

The first close wins. Answering again with the same answer, as the same person, returns `200` with the ask. Any later *different* answer, or one from someone else, and any dismissal after it closed, gets `409 ask_closed`, with the ask as it closed so the client can show who answered. An ask's close is recorded as `ask.closed`, with the ask as it closed.

### Asks and suspension

A session with an open ask is not suspended for being idle. It keeps its agent process for up to 24 hours, so the turn carries on the moment someone answers. After 24 hours its open asks close as `expired`, the turn ends `cancelled` with `reason: "expired"`, and the session is `idle`. An explicit [suspend](/api/http/control#suspend) closes open asks as `interrupted` and cancels the turn. An ask is never open on a suspended session.

### Messages while an ask is open

A message sent while an ask is open is held, not steered: the agent cannot read anything until the ask closes. The send response has `delivery: "held"`, and its `turn` is the running turn. When the last open ask closes, held messages are delivered into the turn in the order they arrived, right after the answer, each recorded as `message.delivered` with `as: "steering"`. If the turn ends first, for example because the answer was a denial the agent stopped on, the held messages start a new turn, with a new turn id.

A message sent with `interrupt` is not held. It interrupts the turn, which closes the ask, and runs.

## Subagents

A **subagent** is an agent the session's agent starts to do part of a turn's work. Each is a [Subagent](/api/reference/objects#subagent), with an `sa_` id, recorded as `subagent.started` and `subagent.ended`. The running ones are in the session's `subagents`.

- A **foreground** subagent runs inside its turn. The turn waits for it, and it ends before the turn does.
- A **background** subagent runs apart from its turn. The turn can complete while it runs, and its events keep arriving under that turn's `turnId` until it ends. The session's `status` describes turns only: an `idle` session with a non-empty `subagents` has background work going on.

| What happens | Foreground subagents | Background subagents |
| --- | --- | --- |
| An [interrupt](/api/http/control#interrupt) | Stopped, with the turn | Keep running |
| A [stop](/api/http/subagents#stop-a-subagent) | Stopped | Stopped |
| An explicit [suspend](/api/http/control#suspend) | Stopped | Stopped |
| Two hours without activity | | The session is not suspended while one runs |

A subagent ends once, as `completed`, `failed` or `stopped`. Read them with [Subagents](/api/http/subagents).

## Who did what

Every event caused by a person carries an `actor`: who, and through which client. Events the agent or the computer caused have `actor: null`. The actor comes from the credential, never from the request body. See [Actor](/api/reference/objects#actor).

## Consistency

- **One writer.** Each session's log is written in one place, the [writer](#one-writer), so every client sees the same events in the same order.
- **Read your writes.** A successful response means the change is in the log. On the same transport, a later read includes it. Across transports, such as a send over the WebSocket followed by an HTTP read, pass the write's `seq` as `minSeq` on the read: it waits up to 2 seconds for the change, or fails with `503 unavailable` and `retryAfterMs`. `opc` and the client library do this for you.
- **Live is not slower than the log.** Over the WebSocket, an event reaches attached clients when it is appended, not after a poll.
- **Lists may lag.** A session in a list can be a few seconds behind its log.
- **A read by id is current as of its `lastSeq`.** The session's `syncedAt` says when its copy last heard from the computer. When the computer is not reachable, it shows how old the snapshot is.
