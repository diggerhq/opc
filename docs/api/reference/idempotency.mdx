---
title: "Idempotency"
description: "Retry any write without doing it twice."
---

A network can drop the response to a request that succeeded. Retrying then could send a message twice or create a second session. An idempotency key prevents that: the server remembers the key, and a retry gets the first answer instead of a second action.

## Use

Send a fresh, random key with each write, and the same key with each retry of it:

```bash
key=$(uuidgen)
curl -s "$API/sessions/$id/turns" -H "x-api-key: $OPENCOMPUTER_API_KEY" \
  -H "content-type: application/json" -H "idempotency-key: $key" \
  -d '{ "input": "run the migration" }'
# no response? retry with the same $key
```

Over the WebSocket, pass `idempotencyKey` in the params. An HTTP route and its WebSocket method are one operation and share keys, so a request sent over one can be retried over the other.

| Accepts a key | |
| --- | --- |
| `POST /sessions` | Creates one session. The response is `200` instead of `201` on a repeat, with the session and turn as they are now. |
| `POST /sessions/{id}/turns`, `turns.send` | Sends one message. `duplicate: true` on a repeat. |
| `POST /sessions/{id}/compact`, `sessions.compact` | Starts one compaction |
| `POST /sessions/{id}/interrupt`, `sessions.interrupt` | Interrupts once. A retry does not interrupt a turn that started after the first. |
| `POST /sessions/{id}/asks/{askId}/answer`, `asks.answer` | Answers once |
| `POST /sessions/{id}/asks/{askId}/dismiss`, `asks.dismiss` | Dismisses once |
| `PUT /sessions/{id}/workspace/archive` | Writes once |

Other writes need no key. Updating settings, cancelling a queued turn, suspending, resuming and setting a secret give the same result when repeated.

## Rules

- **A key is 1 to 255 printable ASCII characters.** A UUID is a good key.
- **Keys are per member and per operation.** The same key from two members, or for two operations, is two keys. A route and its WebSocket method, such as `POST /sessions/{id}/turns` and `turns.send`, are one operation.
- **Keys are kept for 24 hours.** After that, a repeat is a new request.
- **A key identifies the request, not just the call.** A repeat must have the same body: the same `input`, whitespace included, and the same `ifBusy`, where an omitted `ifBusy` equals `queue`. A different body with a used key gets `409 idempotency_conflict` and does nothing.
- **A repeat gets the current state.** A repeated send returns the turn's status now, which may have moved on to `completed`.
- **Concurrent repeats are safe.** If a repeat arrives while the first is still being handled, it waits for that result.
- **Keys hold across restarts.** A session's keys are checked by the session's writer on the computer and recorded in its log, so a retry is recognized even after the computer restarts or the session resumes. Keys for `POST /sessions` are checked before the session exists. Keys for `PUT /sessions/{id}/workspace/archive` and `terminals.open` are the exception: they are kept only while your computer stays up, so a retry after it restarts writes again.

`opc` sends a key with every write, and retries for up to 30 seconds after a lost response before telling you.
