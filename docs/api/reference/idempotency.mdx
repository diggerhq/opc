---
title: "Idempotency"
description: "Retry any write without doing it twice."
---

A network can drop the response to a request that succeeded. Retrying then could send a message twice or create a second session. An idempotency key prevents that: the server remembers the key, and a retry gets the first answer instead of a second action.

## Use

Send a fresh, random key with each write, and the same key with each retry of it:

```bash
key=$(uuidgen)
curl -s "$API/sessions/$id/turns" -H "x-api-key: $OPENCOMPUTER_API_KEY" \
  -H "content-type: application/json" -H "idempotency-key: $key" \
  -d '{ "input": "run the migration" }'
# no response? retry with the same $key
```

Over the WebSocket, pass `idempotencyKey` in the params. HTTP and WebSocket share keys, so a request sent over one can be retried over the other.

| Accepts a key | |
| --- | --- |
| `POST /sessions` | Creates one session. The response is `200` instead of `201` on a repeat. |
| `POST /sessions/{id}/turns`, `turns.send` | Sends one message. `duplicate: true` on a repeat. |
| `POST /sessions/{id}/compact`, `sessions.compact` | Starts one compaction |
| `PUT /sessions/{id}/workspace/archive` | Writes once |

Other writes need no key. Updating settings, answering an ask, interrupting, suspending, resuming and setting a secret give the same result when repeated.

## Rules

- **A key is 1 to 255 printable ASCII characters.** A UUID is a good key.
- **Keys are per member and per route.** The same key from two members, or on two routes, is two keys.
- **Keys are kept for 24 hours.** After that, a repeat is a new request.
- **A key identifies the request, not just the call.** A repeat must have the same body: the same `input`, whitespace included, and the same `mode`, where an omitted `mode` equals `queue`. A different body with a used key gets `409 idempotency_conflict` and does nothing.
- **A repeat gets the current state.** A repeated send returns the turn's status now, which may have moved on to `completed`.
- **Concurrent repeats are safe.** If a repeat arrives while the first is still being handled, it waits for that result.

`opc` sends a key with every message, and retries for up to 30 seconds after a lost response before telling you.
