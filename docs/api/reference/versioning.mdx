---
title: "Versioning"
description: "What can change without notice, what cannot, and how breaking changes would arrive."
---

The API changes by adding, never by breaking. A client written today keeps working.

## What can change at any time

- New routes, methods, query parameters and optional request fields
- New fields in responses, objects, events and errors
- New event types, notifications, error codes, ask kinds and turn failure codes
- New values of fields that list values a client should expect more of: `status`, `delivery`, `via`, `origin.type`, `capabilities.features`, models and modes
- The order of fields in JSON, and the text of `message` fields

So, to keep working: ignore fields and event types you do not know, show unknown statuses as something neutral, and branch on `code`, not `message`.

## What does not change

- The meaning or type of a field
- Required request fields: none are added to existing routes
- Event ordering guarantees, idempotency rules and close codes
- Ids: once issued, an id always refers to the same thing

## The WebSocket protocol version

The WebSocket protocol has a version, chosen when connecting: `opc.v1`. It changes only for a change that cannot be made by adding. When `opc.v2` arrives, servers keep accepting `opc.v1` for at least 12 months, and the changelog says when it will stop. A client that offers only versions the server no longer accepts is closed with `4400`.

The HTTP API has no version number. Its paths will not change meaning. A change that cannot be additive would come as a new route beside the old one.

## Capabilities, not versions

Do not check a version to decide what a session can do. Read [`capabilities`](/api/reference/objects#capabilities). A feature can be off for one organization and on for another, at the same version.

## opc

`opc` is the one client whose builds the server knows. Every request it makes carries `User-Agent: opc/0.1.0`, and when a build is retired, which happens at least 6 months after the one that replaced it shipped, every HTTP request from it is answered `426 upgrade_required` with `minVersion`, and every connection it opens is closed with `4400`. `opc` then exits with code `2` and says which version to install. Nothing is retired without an entry in the [changelog](/changelog) first.

An `opc` that works but is out of date is told so in the `x-opc-latest` header of any response, and says so once a day at most. Other clients are not checked: for them, only the protocol version above matters.
