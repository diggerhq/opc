## API keys

Every HTTP request carries an API key:

```bash
curl "$API/me" -H "x-api-key: $OPENCOMPUTER_API_KEY"
```

`Authorization: Bearer <key>` works too. When both headers are present they must hold the same key, or the request fails with `401 unauthenticated`.

Create keys on the dashboard under **Settings → API keys**. `opc login` creates one as well, named after your machine. Keys do not expire. Revoke one on the same page, or with `opc logout` for the key `opc` created.

A key belongs to the member who created it and acts as that member. It can do exactly what they can, in sessions and in the API, and everything it does is attributed to them, with `via: "api"` or `via: "opc"`. When the member leaves the organization, their keys stop working.

| Key | Can use this API |
| --- | --- |
| A member's key | Yes |
| A key scoped to one OpenComputer project | No: `403 forbidden` with `"reason": "project_key"` |
| A key from another organization | It works in its own organization only. Sessions here are `404`. |

Keys have no finer scopes. To limit what a program can do, give it a separate member account.

<Warning>
A key is as powerful as the member who created it, including in every session they can reach. Keep it in a secret store, never in a repository, a URL or a browser.
</Warning>

## Tickets, for WebSocket connections

A browser cannot set headers on a WebSocket, and the key should never reach one. So a WebSocket connection is opened with a **ticket**: a short-lived token you get over HTTP with your key.

```bash
curl -s -X POST "$API/wire/tickets" -H "x-api-key: $OPENCOMPUTER_API_KEY" \
  -H "content-type: application/json" -d '{ "client": "my-dashboard/1.4.0" }'
```

| | API key | Ticket |
| --- | --- | --- |
| Used for | HTTP requests | Opening WebSocket connections |
| Lifetime | Until revoked | 10 minutes to connect. A connection it opened lasts up to an hour. |
| Safe in a browser | No | Yes, for the member it was issued to |

A server can get tickets with its key and hand them to its own browser clients. See [Tickets](/api/http/tickets).

## Who am I

`GET /me` returns the member, the organization and the computer, and what new sessions start with. `opc whoami` and `opc doctor` print it.

```json
{
  "person": { "id": "usr_2k9d8f7a", "name": "Igor Zalutski", "email": "igor@acme.dev" },
  "organization": { "id": "org_5n1p9w3e", "name": "acme" },
  "credential": { "name": "igor-mbp", "kind": "login", "createdAt": "2026-10-25T18:02:11.000Z" },
  "computer": { "status": "ready", "region": "iad" },
  "defaults": { "model": "claude-opus-5-5", "effort": "high", "mode": "acceptEdits" },
  "capabilities": { "…": "as on a session" }
}
```

| Field | Meaning |
| --- | --- |
| `credential.kind` | `login` for keys `opc login` created, `key` for keys created on the dashboard |
| `computer.status` | `ready`, `asleep` (it starts on first use, which takes seconds) or `not_set_up` |
| `computer.region` | Where the computer runs. Round trips are shortest close to it. |
| `defaults` | The settings a new session gets when the request names none |
| `capabilities` | What a new session would support: the [same object](/api/reference/objects#capabilities) a session has |

Read `capabilities` here to validate a model or mode before creating a session.
